# Add a deck to the Recommended decks tab

## What this is

The Recommended decks tab (`tMeta`, `/meta-decks/`) shows, for each set, three
meta blocks — **early set**, **mid set**, **Set Champs** — and inside each
block one deck per ink pair. Every deck carries a written guide. All of it
comes from one hand-authored file, `meta-decks.json`, which nothing but this
skill and Ben should ever write.

Follow **HOW-WE-WORK.md** in the repo root while doing this: care goes in
before the edit, the reply at the end is 1–3 lines, and the one rule that
never bends is **never hand-edit `index.html` or `flounder-search.html`** —
they're generated by `python3 build_flounder.py`.

## Step 1 — check every card name before anything else

A name that doesn't resolve silently drops a card out of a 60-card deck. Run
the list through the real card data first:

```bash
python3 - <<'PY'
import json, collections
LIST = """PASTE THE DECK LIST HERE"""
db = json.load(open('card-db.json'))
full = {(c['n'] + ' - ' + c['v'] if c.get('v') else c['n']): c for c in db['cards']}
tot = 0; inks = collections.Counter(); curve = collections.Counter(); types = collections.Counter()
for line in LIST.strip().split('\n'):
    line = line.strip()
    if not line: continue
    q, name = line.split(' ', 1)
    q = int(q.rstrip('xX'))
    c = full.get(name.strip())
    if not c:
        print('MISSING:', name); continue
    tot += q
    for i in c['co']: inks[i] += q
    curve[c['c']] += q; types[c['ty']] += q
    kws = [k[0] for k in c.get('kw', []) if k and k[0]]
    print(f"{q:>2} {name:<45} {c['co'][0]:<9} {c['c']}c {c['ty']:<10} "
          f"{c.get('st','-')}/{c.get('wi','-')} lore {c.get('lo','-')} "
          f"{'inkable' if c['ik'] else 'UNINKABLE':<9} {kws}")
    print('    ', (c.get('tx') or '').replace('\n', ' | '))
print()
print('total', tot, '| inks', dict(inks), '| types', dict(types))
print('curve', dict(sorted(curve.items())))
PY
```

Anything that prints `MISSING:` is a typo, a card this site doesn't have yet,
or a name Ben abbreviated — resolve it with him, don't guess a near match.
Names in the file must be the exact `Name - Version` form.

That same output is what you write the guide from. **Read the card text.**
The guide has to be true about these specific cards; a generic archetype
write-up is worse than none, because someone will take it to a tournament.

## Step 2 — work out where it goes

Four things place a deck, and three of them come out of the list itself:

- **set** — the set code from `card-db.json`'s `sets` map (`"13"` is Attack of
  the Vine!). This is the set the deck is *for*, i.e. the current standard, not
  the set its cards happen to come from. Ask if it isn't obvious.
- **block** — `early`, `mid` or `champs`. Ben usually says ("this is the Set
  Champs list", "early meta"). If he doesn't, ask — it isn't guessable.
- **inks** — the two inks the list actually plays, taken from the script above.
- **id** — `<set>-<block>-<ink1>-<ink2>`, lowercase, e.g.
  `13-champs-amber-amethyst`.

One deck per ink pair per block per set. If that slot is already filled,
you're replacing the existing entry, not adding a second — say so and confirm
before overwriting.

## Step 3 — write the guide

Seven fields, and they are the entire reason this tab is worth having. Write
them the way a good player explains a deck to a friend at the table: concrete,
naming actual cards and actual turns. **Ben's site is hand-crafted, not
AI-polished** — plain sentences, no marketing voice, no hype adjectives, no
"powerhouse" or "unmatched" or "meta-defining".

| field | what it is |
|---|---|
| `why` | 3–5 sentences of prose. Why the 60 cards are these 60 — the engine, what supports it, why the removal is split the way it is. |
| `lines` | 5–8 short entries. Real sequences: "turn 1 X, turn 3 Shift Y onto it". Name the turn and the cards. |
| `against` | 3–5 entries. What actually beats it, with the reason — "Gaston needs 5 strength, so a swarm of medium bodies dodges it". |
| `mulligan` | 2–4 sentences of prose. What to keep, what to ship, and why. |
| `priorities` | 4–6 entries. In-game decisions, in rough turn order. |
| `strengths` | 3–5 short entries. |
| `weaknesses` | 3–5 short entries. Be honest. A deck with no listed weakness reads as an advert. |

Also set `name` (e.g. "Amber/Amethyst Midrange"), `archetype` (one line, the
plan in a breath), `updated` (today), and `credit` — **ask whose list it is**.
If a player or a team built it, name them; if Ben doesn't know or it's his own,
leave it `""`.

Counting things beats claiming them: count the uninkables, count the
characters, count the 1-lore bodies, check the curve. Those numbers are what
make a guide sound like it was written by someone who read the list.

## Step 4 — write it into meta-decks.json

Append to `decks`. Don't reformat the rest of the file, and don't touch
`blocks` unless Ben asks for different block names. Bump the top-level
`updated`.

Do it with a script rather than by hand — the file is JSON and a stray comma
takes the whole tab down:

```bash
python3 - <<'PY'
import json, collections
p = 'meta-decks.json'
d = json.load(open(p))
entry = { ... }                      # the full deck object
d['decks'] = [x for x in d['decks'] if x['id'] != entry['id']] + [entry]
d['updated'] = entry['updated']
json.dump(d, open(p, 'w'), indent=2, ensure_ascii=False)
open(p, 'a').write('\n')
PY
```

## Step 5 — build, and read what the build says

```bash
python3 build_flounder.py 2>&1 | grep -E "meta decks|  !"
```

The build validates this file on every run: unknown card names, unknown block
or set, a declared ink pair that disagrees with the cards, a duplicate
set/block/ink slot, and a deck that isn't 60 cards. **Every `!` line is a real
problem — fix it, don't ship past it.** A clean run prints only the
`meta decks: N across M set(s)` line.

Screenshot the tab so he can see the tile and the guide as published:

```bash
node - <<'EOF'
const {chromium}=require('/tmp/node_modules/playwright-core');

  const b=await chromium.launch();

EOF
kill $(cat /tmp/httpd.pid) 2>/dev/null
```

Send him the screenshot, then say in one or two lines what you added and ask
whether to push. **Don't push to `main` on your own** — pushing is shipping
live on this repo, and the guide text is opinion he may want to change.

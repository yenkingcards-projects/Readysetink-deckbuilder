# Review art tag improvements

## Why this exists

`art-tags.json` is the data that makes the site's "describe what you remember
seeing" search work. It's built by a local Ollama vision model
(`art-tools/tag_art.py` and friends, kicked off via the
`Start Tagger Improvement` / `Start Tagging` `.command` files) reading card
art and guessing short descriptive tags. That model is good, not perfect — it
occasionally leaks its own JSON syntax into a tag string, leaks a fragment of
its own reasoning, or produces something digit-contaminated or absurd. This
skill is the QA gate between "the tagger ran" and "this is live on the site."

It's meant to run unattended by a fresh session with no memory of any prior
conversation — everything it needs to know is below or in the files it
reads. Follow **HOW-WE-WORK.md** in the repo root for tone while doing this:
no verification theatre beyond what's actually described here, batch what
you find into one report, reply tersely. And the one rule that never bends:
**never hand-edit `index.html` or `flounder-search.html`** — they're
generated by `python3 build_flounder.py` from `flounder-search.template.html`
and `art-tags.json`; if a fix belongs anywhere, it belongs upstream of the
build, never in the build output.

## Step 1 — see what actually changed

```bash
git status -s art-tags.json
git diff --stat -- art-tags.json
tail -40 art-tools/overnight-run.log
```

`art-tools/set-outputs/*.json` (the raw per-set tagger output) is gitignored,
so `git diff` won't show it — that's expected, not a problem. Check which
sets the log says were just processed, and cross-reference against master:

```bash
python3 -c "
import json, glob, os
with open('art-tags.json') as f: master = json.load(f)['cards']
for p in sorted(glob.glob('art-tools/set-outputs/*-art-tags.json')):
    with open(p) as f: data = json.load(f)
    missing = [k for k in data.get('cards', {}) if k not in master]
    if missing:
        print(f'{os.path.basename(p)}: {len(missing)} cards not yet in master')
"
```

If anything shows up missing, that set's output never got merged (this has
happened before, from a crashed run) — merge it before moving on:
`python3 art-tools/merge_art_tags.py --input <file> --dry-run` first to check
for unknown-name warnings, then for real without `--dry-run`.

## Step 2 — clean it up

The improve/run-everything pipelines already run `fix_leaked_json.py` and
`clean_slop.py` automatically now, so this step is usually a no-op — but
"usually" is exactly why it's still worth running: it costs nothing when
there's nothing to fix, and it's the safety net for anything that slipped
through (an interrupted run, a manual merge you just did in Step 1, an older
set that predates these fixes being wired in).

```bash
python3 art-tools/fix_leaked_json.py art-tags.json
python3 art-tools/clean_slop.py
```

Both print what they changed and write a timestamped backup before touching
anything. Read the output — if either one reports real numbers, that's worth
one line in your final report; if both say "nothing to clean," don't mention
it, that's the expected case.

## Step 3 — check scope

Two different things, both matter:

**Nothing unexpected got touched.** `git status -s` should show
`art-tags.json` (and, after Step 4's rebuild, the generated files:
`index.html`, `flounder-search.html`, `flounder-tagger.html`,
`flounder-notes.html`, `sitemap.xml`, `BUILD-REPORT.md`) — nothing else. If
anything outside that list changed, stop and say so; don't guess why.

**The tags themselves are plausible.** This is the part that genuinely needs
a look, not a script — slop-cleaning catches syntax garbage, not content
that's syntactically fine but wrong. Pick a real sample: every card that's
new since the last review (from Step 1's set-output diff), or if that's a
lot, at least 15–20 spread across different cards, and read their `"a"` tag
lists yourself. You're looking for:
- Tags that plainly don't describe the card (wrong character, wrong colors,
  wrong scene — something a glance at the art would contradict)
- Anything that reads like a hallucinated guess dressed up as a tag rather
  than an actual visual description
- Suspiciously generic filler that doesn't earn its place ("image", "card",
  "picture")

A card page is at `card/<slugified-name>.html` after the build in Step 4, or
you can just read the tag list straight out of `art-tags.json` — you don't
need the rendered page to judge whether "blue dress" is a reasonable tag for
a card named "Elsa - Ice Queen." Don't open every card in a browser; that's
the verification-theatre HOW-WE-WORK.md warns against. Reading the tag
strings against the card names is enough for the sample.

Only escalate to Ben what actually needs his judgment — a specific tag you
genuinely can't tell is wrong or right, or a scope surprise. Don't list every
tag you checked and approved; that's noise, not signal.

## Step 4 — rebuild and get a real snapshot

```bash
python3 build_flounder.py
```

Read its own output closely — it already reports tagged/searchable card
counts and **will refuse to ship** ("DO NOT SHIP THIS BUILD") if it finds a
hand-authored name that stopped resolving. Treat that refusal as real: find
out why before doing anything else, don't route around it.

Then make the change concrete instead of just reporting a number. Pick 2–3
of the cards from your Step 3 sample and show their actual before/after tag
list (before = the git-diffed old `art-tags.json`, after = the new one) —
e.g. `git show HEAD:art-tags.json` (or your last-reviewed commit) piped
through the same small Python snippet as Step 1, diffed against the current
file for those specific card keys. That's the "snapshot": not a screenshot,
not a card page render — the actual words that are new, for cards Ben will
recognize by name. If a local preview server is genuinely useful (Ben asks
to see it, or something about a tag's effect on search is easier shown than
described), use it — but it's not required for every review.

## Step 5 — ask, don't assume

Once Steps 2–4 are done and reported, ask Ben what he wants to do next —
use AskUserQuestion with options along these lines:

- **Ship it** — get this onto the live site (push / open a PR, matching
  however you've been shipping other changes with him)
- **Hold it** — he wants to make other feature changes first and bundle them
- **Not yet** — something in your report needs fixing before it goes anywhere

Don't default to shipping automatically just because the checks passed —
he's asked to be asked, every time.

## Report format

Keep it to what HOW-WE-WORK.md asks for: what changed, what you fixed, what
(if anything) needs his call, then the snapshot from Step 4. Skip the
recap of steps you took that found nothing — "ran clean_slop, nothing to
clean" is one clause, not a paragraph.
